- Объединять несколько компонентов в один
- Реализовывать мультиадаптер через композицию
- Управлять порядком компонентов
- Выбирать между композицией и множественным наследованием

Иногда компонент должен вести себя как несколько других компонентов одновременно. Например, текст может состоять из нескольких частей, а каталог — из нескольких файлов. Для этого используется **мультиадаптер** — компонент, который агрегирует несколько источников.

## Композитный компонент

```logtalk
:- object(composite_text(_Components_),
    implements(text_p)).

    text(Result) :-
        findall(Text,
            (   lists:member(Component, _Components_),
                Component::text(Text)
            ),
            Texts),
        atomic_list_concat(Texts, Result).

:- end_object.
```

Запрос:

```logtalk
?- composite_text([
       plain_text(foo),
       plain_text(bar)
   ])::text(Text).
Text = foobar.
```

Мультиадаптер реализует тот же протокол `text_p`, но его поведение складывается из поведения вложенных компонентов. Клиент не знает, что перед ним композиция.

## Порядок имеет значение

В примере выше `findall/3` сохраняет порядок обхода списка. Если поменять компоненты местами, результат изменится:

```logtalk
?- composite_text([
       plain_text(bar),
       plain_text(foo)
   ])::text(Text).
Text = barfoo.
```

Для операций, где порядок не важен (например, сумма размеров), это не критично. Для текста, конвейера обработки или журнала порядок нужно явно документировать.

## Композиция вместо множественного наследования

Мультиадаптер можно было бы попытаться построить через множественное наследование:

```logtalk
:- object(composite,
    extends(a),
    extends(b)).
```

Но такой подход хрупок: методы с одинаковыми именами конфликтуют, а порядок разрешения конфликтов зависит от реализации. Композиция через список компонентов проще:

- явно видно, из чего состоит объект;
- можно менять состав во время выполнения;
- легко добавить новый компонент;
- не возникает конфликтов имён.

## Мультиадаптер с ограничениями

Мультиадаптер может проверять, что все компоненты реализуют нужный протокол:

```logtalk
:- object(checked_composite(_Components_),
    implements(text_p)).

    text(Result) :-
        forall(
            lists:member(Component, _Components_),
            Component::implements_protocol(text_p)
        ),
        ...

:- end_object.
```

Такой объект отказывается работать с неподходящими компонентами и сообщает об ошибке на раннем этапе.

## Когда мультиадаптер не нужен

- Если компоненты независимы, не объединяйте их в один объект.
- Если нужен только один источник, используйте обычный адаптер.
- Если состав фиксирован и прост, достаточно явного объекта с методами.

## Что важно запомнить

- Мультиадаптер агрегирует несколько компонентов с общим интерфейсом.
- Композиция через список компонентов обычно лучше множественного наследования.
- Порядок компонентов влияет на результат.
- Проверка протоколов помогает отловить ошибки конфигурации.
