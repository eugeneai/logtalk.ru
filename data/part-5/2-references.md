В предыдущем разделе мы создавали экземпляры через `new/1`, но почти не хранили в них данные. В объектно-ориентированной программе экземпляр обычно обладает собственным состоянием: счётчик хранит текущее значение, студент — имя и оценки, игровой персонаж — координаты и здоровье.

В Logtalk состояние экземпляра можно организовать несколькими способами. Самый простой и предсказуемый — использовать **категорию с динамическим предикатом**, как в учебнике Logtalk «Dynamic object attributes». Категория импортируется в класс, а её методы обращаются к динамическому предикату через `::`, то есть в контексте конкретного экземпляра.

## Категория состояния счётчика

```logtalk
:- category(count_state).

    :- public(set_count/1).
    :- public(get_count/1).

    :- private(count_/1).
    :- dynamic(count_/1).

    set_count(Count) :-
        ::retractall(count_(_)),
        ::assertz(count_(Count)).

    get_count(Count) :-
        ::count_(Count).

:- end_category.
```

Ключевая деталь — вызовы `::retractall/1`, `::assertz/1` и `::count_/1`. Они выполняются в контексте **того объекта, который импортировал категорию**, а не в контексте самой категории. Поэтому у каждого экземпляра будет свой собственный предикат `count_/1`.

Теперь определим класс `counter`:

```logtalk
:- object(counter,
    instantiates(class),
    specializes(object),
    imports(count_state)).

    :- public(value/1).
    :- public(increment/0).

    value(Value) :-
        (   ::get_count(Value)
        ->  true
        ;   Value = 0
        ).

    increment :-
        (   ::get_count(Count)
        ->  true
        ;   Count = 0
        ),
        Next is Count + 1,
        ::set_count(Next).

:- end_object.
```

Создадим два экземпляра и проверим, что их состояние не разделяется:

```logtalk
?- counter::new(C1), counter::new(C2).
C1 = ...
C2 = ...

?- C1::value(V1).
V1 = 0.

?- C1::increment, C1::value(V1), C2::value(V2).
V1 = 1,
V2 = 0.
```

Если бы `count_/1` был объявлен прямо в классе `counter`, то динамический предикат принадлежал бы классу и все экземпляры видели бы одно и то же значение. Именно поэтому состояние вынесено в категорию и обновляется через сообщение к самому себе.

## Создание экземпляров через create_object/4

Метод `new/1` из метакласса `class` — это удобная обёртка над встроенным предикатом `create_object/4`:

```logtalk
create_object(Instance, Relations, Directives, Clauses)
```

Например, создать экземпляр класса `counter` можно и напрямую:

```logtalk
?- create_object(my_counter, [instantiates(counter)], [], []).
true.

?- my_counter::value(Value).
Value = 0.
```

Аргументы `create_object/4`:

- `Instance` — имя нового объекта;
- `Relations` — отношения с другими объектами, например `[instantiates(counter)]`;
- `Directives` — директивы объекта, например `[public(foo/1), dynamic(bar/1)]`;
- `Clauses` — начальные предложения объекта.

Прямой вызов полезен, когда нужно создать объект с дополнительными директивами или начальными фактами. В большинстве случаев достаточно метода `new/1`.

## Уничтожение динамических объектов

Динамический объект можно удалить предикатом `abolish_object/1`:

```logtalk
?- abolish_object(my_counter).
true.

?- current_object(my_counter).
false.
```

Уничтожать можно только динамические объекты. Если попытаться удалить статический объект, объявленный в исходном файле, Logtalk выбросит исключение.

## Динамические объекты и динамические предикаты

Не путайте два разных понятия:

- **динамический объект** создаётся во время выполнения и может быть уничтожен;
- **динамический предикат** — это предикат, факты которого можно добавлять и удалять через `assertz/1`, `retract/1` и `retractall/1`.

Динамический предикат может находиться и в статическом объекте. Например, реестр из следующего раздела — статический объект с динамическим предикатом внутри.

## Связь с функциональным программированием

В Haskell состояние обычно передаётся явно: функция получает старое состояние и возвращает новое. В Logtalk можно поступить так же — передавать состояние аргументами. Динамические предикаты дают другой стиль: состояние хранится внутри объекта и изменяется сообщениями. Этот стиль удобен для моделирования объектов предметной области, но требует дисциплины: состояние должно быть локальным для объекта и не должно неожиданно разделяться между экземплярами.
