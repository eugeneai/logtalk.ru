В предыдущем разделе мы увидели, что событие возникает при отправке сообщения через `::/2`. Теперь рассмотрим, как монитор принимает и обрабатывает эти события.

## Обработчики событий

Монитор реализует протокол `monitoring`:

```logtalk
:- object(audit,
    implements(monitoring)).

    before(Object, Message, Sender) :-
        format('before: ~w <- ~q from ~w~n',
               [Object, Message, Sender]).

    after(Object, Message, Sender) :-
        format('after: ~w <- ~q from ~w~n',
               [Object, Message, Sender]).

:- end_object.
```

`before/3` вызывается до выполнения метода. `after/3` — после успешного выполнения. Если метод завершился неудачей, событие `after` не генерируется.

## Подписка и отписка

```logtalk
?- set_logtalk_flag(events, allow).
?- define_events(_, _, _, _, audit).
```

`define_events/5` принимает пять аргументов:

```logtalk
define_events(Event, Object, Message, Sender, Monitor)
```

- `Event` — `before` или `after` (или переменная для обоих);
- `Object` — объект-получатель;
- `Message` — сообщение;
- `Sender` — отправитель;
- `Monitor` — объект-монитор.

Если часть аргументов не указана, подписка действует на множество событий.

Отписка:

```logtalk
?- abolish_events(_, _, _, _, audit).
```

Перечисление активных событий:

```logtalk
?- current_event(Event, Object, Message, Sender, Monitor).
```

## Семантика мониторов

Мониторы могут влиять на выполнение сообщения:

- если `before/3` завершается неудачей, сообщение не выполняется;
- если `after/3` завершается неудачей, сообщение считается неуспешным;
- порядок вызова нескольких мониторов не определён.

Поэтому обработчик монитора должен либо всегда завершаться успешно, либо осознанно блокировать сообщение. Для логирования обычно используют обработчик, который не может потерпеть неудачу.

## Пример: счётчик сообщений

```logtalk
:- object(counter_monitor,
    implements(monitoring)).

    :- private(count_/1).
    :- dynamic(count_/1).

    before(Object, _Message, _Sender) :-
        Object == greeter, !,
        (   count_(Count)
        ->  true
        ;   Count = 0
        ),
        Next is Count + 1,
        retractall(count_(_)),
        assertz(count_(Next)).
    before(_, _, _).

    after(_, _, _).

    count(Count) :-
        (   count_(Count)
        ->  true
        ;   Count = 0
        ).

    reset :-
        retractall(count_(_)).

:- end_object.
```

Такой монитор считает только сообщения, отправленные объекту `greeter`. Сообщения самому монитору не увеличивают счётчик.

## Область видимости обработчиков

`monitoring` объявляет `before/3` и `after/3` публичными. Если нужно, можно использовать защищённую или приватную реализацию протокола, чтобы другие объекты не вызывали обработчики напрямую. Механизм событий всё равно сможет их вызвать.

## Что важно запомнить

- `before/3` и `after/3` — обработчики событий монитора.
- `define_events/5` подписывает, `abolish_events/5` отписывает, `current_event/5` перечисляет.
- Ошибка монитора может заблокировать сообщение.
- Обработчики должны быть предсказуемыми и не мешать основной логике.
