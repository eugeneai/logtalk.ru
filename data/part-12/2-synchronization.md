После изучения этого раздела вы сможете

- Организовывать обмен сообщениями между потоками
- Использовать `threaded_notify/1` и `threaded_wait/1`
- Проверять очередь без блокировки через `threaded_peek/1`
- Запускать односторонние задачи через `threaded_ignore/1`

</text-box>

Потоки не должны обращаться к общим изменяемым данным без согласования. В Logtalk есть простой механизм уведомлений: один поток отправляет терм, другой ждёт его в очереди сообщений объекта.

## Уведомление и ожидание

```logtalk
:- object(notify_demo).
    :- threaded.

    :- public(run/0).

    run :-
        threaded((
            producer,
            consumer
        )).

    producer :-
        threaded_notify(item(42)),
        write(producer_done), nl.

    consumer :-
        threaded_wait(item(X)),
        write(consumed(X)), nl.

:- end_object.
```

```logtalk
?- notify_demo::run.
producer_done
consumed(42)
```

`threaded_notify/1` отправляет уведомление в очередь текущего объекта и не блокируется. `threaded_wait/1` приостанавливает поток до появления подходящего уведомления.

Порядок вывода может меняться: потоки выполняются параллельно.

## Очередь сообщений

Уведомления хранятся в очереди объекта. Если отправить несколько сообщений подряд, получатель заберёт их по одному:

```logtalk
producer :-
    threaded_notify(step(1)),
    threaded_notify(step(2)),
    threaded_notify(done).

consumer :-
    threaded_wait(step(N)),
    write(step(N)), nl,
    ( N =:= 2 -> threaded_wait(done) ; consumer ).
```

`threaded_wait/1` ищет первое уведомление, которое унифицируется с образцом. Если нужен строгий порядок, используйте разные шаблоны и явные состояния.

## Проверка без блокировки

`threaded_peek/1` проверяет, есть ли уведомление, но не удаляет его из очереди:

```logtalk
process :-
    ( threaded_peek(item(X)) ->
        threaded_wait(item(X)),
        handle(X)
    ;   write(no_items), nl
    ).
```

Частый `threaded_peek/1` в цикле — это опрос очереди. Он может расходовать процессорное время, поэтому лучше комбинировать его с `thread_sleep/1` или строить схему на блокирующем `threaded_wait/1`.

## Односторонние задачи

`threaded_ignore/1` запускает цель в отдельном потоке и не ждёт её результата:

```logtalk
log_later(Event) :-
    threaded_ignore(write_log(Event)).
```

Это удобно для фоновой записи, отправки метрик или уведомления внешней системы. Ошибки такого потока не возвращаются вызывающему коду, поэтому их нужно обрабатывать внутри цели.

## Отмена

`threaded_cancel/1` отменяет поток, запущенный через `threaded_call/1` или `threaded_once/1`, если он ещё работает. Используйте отмену осторожно: поток может находиться в середине изменения данных.

## Что важно запомнить

- `threaded_notify/1` отправляет уведомление в очередь текущего объекта.
- `threaded_wait/1` блокирует поток до подходящего уведомления.
- `threaded_peek/1` проверяет очередь, не удаляя сообщение.
- `threaded_ignore/1` запускает фоновую цель без ожидания результата.
- Обмен уведомлениями не заменяет полноценную синхронизацию общих данных.
